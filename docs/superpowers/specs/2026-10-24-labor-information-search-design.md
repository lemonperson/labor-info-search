# 劳动权益公开信息检索工具——产品设计

## 1. 产品意图

本项目是一款面向普通消费者的 Windows 本地桌面工具。消费者在购买商品前，可以输入企业或品牌名称、粘贴商品链接，或上传商品详情/包装截图；工具帮助识别相关企业主体，并检索、整理互联网上公开可访问的劳动权益信息。

产品的价值立场是：许多消费者本身也是劳动者，他们应当更容易了解一家企业如何对待劳动者，并据此作出自己的消费选择。

工具只降低信息检索与核验门槛，不替用户判断企业“好”或“坏”，不生成购买建议，也不建立企业黑名单。

## 2. 目标用户与成功标准

### 目标用户

- 不会编程、没有开发环境的普通 Windows 消费者。
- 希望在购买前了解品牌方、生产商或店铺经营者劳动用工相关公开信息的人。
- 愿意阅读来源和上下文，自主形成判断的人。

### 成功标准

- 用户不需要注册账号、填写 API 密钥或安装 Python/Node.js 等开发工具。
- 用户可以从 GitHub Releases 下载后直接安装或解压运行。
- 从打开软件到发起一次企业检索，不超过三个清晰动作。
- 每条结果都能看到来源性质、发布者、日期、原文入口和核验状态。
- 品牌方、店铺经营者、生产商和代工方不会在未确认时被合并成同一主体。
- 自动检索失败时，用户仍能在明确知情并确认后，通过外部浏览器继续搜索。
- 页面保持高信息可读性，不依靠评分、强烈警示色或情绪化措辞引导结论。

## 3. 非目标与反目标

### 非目标

- 不判断企业是否“良心”“黑心”或是否值得购买。
- 不提供企业劳动表现评分、排行榜、红黑榜或抵制名单。
- 不保证覆盖整个互联网，也不保证搜索结果没有遗漏。
- 不绕过登录、验证码、付费墙、访问控制或平台反自动化机制。
- 不采集非公开个人信息，不尝试识别匿名发帖人的真实身份。
- 第一版不支持 macOS 和 Linux，不承诺移动端应用。
- 第一版不承诺覆盖境外企业或外文公开来源。
- 第一版不建设中心化后端、用户账号体系或云端搜索历史。

### 反目标（即使功能可用也算失败）

- 将个人指控写成已经确认的事实。
- 因同名企业、品牌与代工关系混淆而把信息归到错误主体。
- 只展示投诉或最初报道，而隐藏能够找到的企业回应、撤诉、澄清、裁判结果或整改后续。
- 软件未经确认自行打开外部浏览器、上传截图或发送检索历史。
- 为追求“全网”宣传而采用脆弱、违规或不可持续的抓取方式。
- 用空洞的大面积留白代替设计，或用卡片、渐变、徽章和装饰堆满页面。

## 4. 已确定的产品约束

- 首发平台：Windows 10/11。
- 地域与语言：第一版聚焦中国大陆企业和中文公开来源；境外企业、外文来源、多语言查询与 OCR 留到后续版本。
- 形态：可安装或免安装的桌面应用，普通用户双击即可使用。
- 成本：基础功能完全免费。
- 身份：无需注册账号。
- 配置：无需用户提供任何 API 密钥。
- 网络：公开信息检索需要联网；OCR、历史和结果整理尽可能在本机完成。
- 发布：完整源代码、中文文档和可执行版本发布到 GitHub。
- 中立性：不评分、不贴标签、不生成主观购买建议。
- 外部浏览器：只能在用户明确确认后打开。
- 主体确认：免费公开信息不足时，允许用户确认品牌名或企业关键词后继续，但必须显示“主体尚未权威核验”，并在结果中保留匹配依据；不能伪装成工商登记核验结果。

## 5. 考虑过的实现路线

### 路线 A：下载源码后运行本地网页

优点是开发和跨平台成本低；缺点是用户必须安装运行环境并使用命令行，与普通消费者的使用能力不匹配，因此排除。

### 路线 B：本地服务启动后自动打开浏览器

可以打包成双击程序，搜索和 OCR 能力也较容易实现；但体验仍像本地网站，系统防火墙、端口和浏览器切换可能让非技术用户困惑。它可作为内部实现或故障降级方式，不作为首选外观。

### 路线 C：桌面应用，内部使用 Web 技术（已选择）

用户获得普通 Windows 软件体验，界面开发效率高，也能继续保留未来移植能力。代价是安装包更大、打包与升级流程更复杂，但与“普通消费者无需开发环境”的目标最一致。

### 实现建议（留给开发计划确认）

优先选择成熟的 Web 桌面容器与 TypeScript 前端。Electron 更易将网络请求、页面解析、本地数据库和 OCR 统一打包，代价是安装包较大；Tauri 安装包较小，但复杂解析/OCR往往需要额外 sidecar 或 Rust 适配。第一版应优先降低实现与调试风险，而不是追求最小安装包。最终框架由开发计划在验证 OCR、打包和网页解析原型后确定。

## 6. 信息输入与完整用户流程

### 6.1 三个入口

1. **企业名称**：输入品牌、企业或厂商名称。
2. **商品链接**：支持淘宝、京东、抖音、拼多多链接的尽力识别。
3. **上传截图**：上传商品详情、包装标签或企业信息截图，在本机 OCR。

三个入口最终都进入“确认企业主体”，之后共用同一检索流程。

### 6.2 企业名称入口

1. 用户输入名称。
2. 工具生成可能的企业主体候选。
3. 候选显示完整名称和能够可靠取得的辅助字段。
4. 用户确认目标主体，或选择“仅按当前关键词搜索”。

### 6.3 商品链接入口

1. 用户粘贴链接。
2. 工具跟随正常公开重定向，读取无需登录即可获得的页面元数据、结构化数据和正文标识。
3. 尽力提取商品名称、品牌、店铺经营者、生产商/委托方。
4. 对无法可靠确定的关系标记“尚未确认”，绝不自动等同。
5. 用户从候选中确认调查主体；读取失败时建议上传截图或手动输入。

平台页面可能需要登录、动态加载或触发访问限制，因此“支持某平台”表示提供识别适配和合理降级，不承诺所有链接都能自动解析。

### 6.4 截图入口

1. 用户选择本地图片。
2. OCR 在本机运行，不默认上传。
3. 工具识别“品牌、制造商、生产企业、委托方、经销商”等关键词附近的文本。
4. 展示提取文本和企业候选，让用户修正并确认。
5. 图片默认只用于本次处理，不长期保存原图；若用户选择保存记录，只保存必要的文本结果。

### 6.5 检索

1. 根据已确认主体生成多组劳动权益查询词。
2. 通过可插拔来源连接器检索公开可访问的信息。
3. 连接器遵守限速、缓存和公开访问边界，不绕过限制。
4. 对结果执行主体匹配、去重、来源分类和事件关联。
5. 展示结果，并明确自动检索可能不完整。

建议的查询主题包括：欠薪、劳动仲裁、劳动合同、违法解除、裁员、加班、工时、社保、工伤、安全生产、行政处罚、劳动保障监察、员工待遇、工会及企业回应等。词表是检索工具，不代表结果已经成立。

### 6.6 外部浏览器补充检索

当自动检索不足或连接器受限时，应用显示一个非强迫式提示，列出：

- 为什么建议继续搜索；
- 将打开的搜索服务；
- 即将使用的查询关键词；
- 浏览器内容由外部网站提供；
- 工具不会自动收集用户之后的浏览记录。

按钮为“取消”和“确认并打开浏览器”。只有点击确认后才调用系统默认浏览器。每次打开都需要当次确认，第一版不提供永久跳过确认。

## 7. 信息来源与中立呈现

### 7.1 来源类型

- 政府通报、行政处罚及其他正式监管记录；
- 法院裁判、仲裁相关公开记录（在合法且公开可访问时）；
- 正规媒体报道；
- 企业公告、企业公开回应；
- 员工或自称员工在公开社交平台的陈述；
- 其他可公开核验的网页材料。

### 7.2 必显示字段

每条结果尽可能展示：

- 原始标题；
- 来源类型；
- 发布者或网站名称；
- 发布时间及抓取时间；
- 客观原文摘录；
- 原文链接；
- 匹配到的企业主体及匹配依据；
- 是否属于个人陈述、是否经过独立确认；
- 关联的企业回应、裁判结果、澄清、撤诉或整改后续；
- 页面失效或原文删除状态（如已知）。

### 7.3 摘要规则

- 第一版不依赖云端大模型生成摘要。
- 优先展示原文中的可核验摘录及关键词上下文。
- 可以做规则化压缩和重复句清理，但不得补写因果、动机或定性判断。
- 原文中的情绪化措辞应明确属于原作者，不转换成工具自身口吻。
- “据某用户陈述”“企业回应称”“裁判文书载明”等归属语必须保留。

### 7.4 排序与筛选

默认排序依据是相关性和时间，不使用“恶劣程度”。用户可切换时间排序，并按来源类型筛选。所有筛选名称应为事实类别，不使用价值标签。

## 8. 信息关联与主体防误配

工具应把以下主体作为不同实体：

- 商品销售店铺及其经营者；
- 品牌及品牌权利人；
- 母公司、子公司和关联公司；
- 委托方、生产企业和代工厂；
- 平台经营者。

自动识别结果必须带置信说明或匹配依据。置信不足时要求用户确认，不以醒目百分比分数制造“算法确定性”。

同一事件中的最初陈述、媒体跟进、企业回应、监管处理和后续结果应聚合为一个事件链，但每个来源仍保留独立出处与发布时间。

## 9. 界面与视觉设计

### 9.1 已选择的方向

采用“留白聚焦”布局。它以单一主要任务为中心：输入或确认调查对象，然后阅读结构清晰的结果列表。

### 9.2 视觉原则

- 参考高品质消费级工具的克制感，而不是直接复制任何品牌界面。
- 简约不等于空：使用明确的排版尺度、精确留白、细腻分隔、柔和材质和轻微动效建立层次。
- 使用系统字体栈，优先保证中文显示质量。
- 主界面限制同时出现的强调色数量；状态差异首先靠文字和布局表达。
- 避免大面积营销渐变、玻璃拟态滥用、发光边框、密集图标和卡片套卡片。
- 动画用于解释状态变化：检索、主体确认、列表到详情的过渡；遵守系统“减少动态效果”设置。
- 默认提供浅色主题；架构支持深色主题，是否在首版开放由开发计划按工作量决定。

### 9.3 主界面结构

1. 极简顶部栏：产品名称、信息说明、设置。
2. 核心标题与一句边界说明。
3. 三种输入方式的紧凑切换。
4. 单一主输入区与“开始检索”。
5. 本地处理和外部浏览器确认提示。
6. 检索后在同一页面进入结果状态，顶部标题区适度收拢。
7. 结果列表只显示阅读决策必需的信息。

### 9.4 结果列表

单条结果展示来源类型、发布者、日期、标题、客观摘录和进入详情的提示。列表不显示评分、危险等级或购买建议。筛选和排序放在列表标题附近，不制作仪表盘式统计卡。

### 9.5 详情视图（设计方决定）

点击结果进入独立详情视图，并使用克制的页面转场。详情包含原文信息、较长摘录、主体匹配依据、相关事件链、企业回应和后续。返回后保留原列表滚动位置和筛选状态。

采用独立详情而不是列表内无限展开，原因是后者会破坏结果扫描节奏并造成页面高度失控。

### 9.6 空状态与错误状态

- 无结果：说明“未检索到不代表不存在”，提供调整企业主体、修改关键词和经确认后打开浏览器三种后续动作。
- 链接读取失败：说明可能原因，保留链接，推荐截图或手动输入。
- OCR 置信不足：展示识别文本供修改，不自动发起企业检索。
- 网络不可用：说明哪些本地功能仍可使用，并允许稍后重试。
- 来源失效：保留已记录的标题、日期和失效状态，但不伪造原文内容。

## 10. 本地数据、隐私与安全

- 不设置遥测和广告标识；第一版默认不发送使用统计。
- 检索历史与缓存只存本机，提供“清除历史与缓存”。
- 默认保存最近检索以便返回查看，但首次使用时清楚说明；设置中可关闭历史记录。
- 截图默认不长期保存；只保留用户确认后的必要文本与结果引用。
- 外部链接在系统默认浏览器中打开，打开前显示目标域名。
- 对网页内容进行严格转义/净化，不执行来源网页脚本，不把网页内容当作应用指令。
- 网络请求有超时、体积上限、内容类型校验和并发限制。
- 不允许来源网页读写本地文件或调用桌面高权限能力。

## 11. 无密钥检索策略

商业搜索 API 通常需要密钥或付费，公开桌面应用也不能安全内置共享密钥。因此采用混合策略：

1. 可插拔的公开来源连接器；
2. 合理限速、缓存和失败隔离；
3. 不绕过验证码或访问限制；
4. 自动检索失败不影响已有结果；
5. 用户确认后在外部浏览器继续搜索；
6. 产品文案不使用“搜尽全网”等无法证明的承诺。

开发计划需要先做一个技术验证，确认首批无密钥来源的稳定性和使用边界，然后决定第一版内置连接器清单。连接器失效必须可以独立关闭或更新，不能导致整个应用无法使用。

## 12. 本地历史与结果状态

每次检索记录建议包含：查询方式、用户确认的企业主体、生成的查询词、结果引用、检索时间和连接器状态。用户可以删除单条记录或清空全部记录。

页面正文不应永久复制大段第三方内容；缓存以必要的索引字段和短摘录为主，原文由链接回到来源核验。

## 13. 可访问性与易用性

- 可全程使用键盘操作，焦点状态清楚。
- 文字、按钮和输入框满足合理对比度与点击面积。
- 不单独依靠颜色表达来源或状态。
- 错误提示说明下一步，不只显示技术错误码。
- 专业术语提供简短解释，例如“企业主体”“公开陈述”“尚未独立核验”。
- 应用启动、OCR和检索过程都有可理解的进度与取消入口。

## 14. GitHub 交付物

- 完整源代码与构建配置；
- 中文 `README.md`，包含产品边界、下载安装、使用方法和截图；
- Windows 安装包，条件允许时同时提供免安装压缩包；
- MIT 开源许可证，允许个人与组织使用、修改和再发布，同时保留版权与许可声明；这是设计方基于“让任何人都能下载使用”的默认选择。
- `PRIVACY.md`：本地数据、联网行为和外部浏览器说明；
- `SOURCES.md`：来源类型、摘录和中立呈现规则；
- `DISCLAIMER.md`：信息可能遗漏或变化，用户应核验原文；
- `CONTRIBUTING.md`：新增来源连接器与平台解析器的贡献规范；
- GitHub Issues 模板：链接解析失败、来源纠错、主体误配和功能建议；
- 自动构建与基础测试流程；
- 发布说明和已知限制。

项目名称尚未由用户确定。开发期间使用中性工作名“劳动信息检索”，避免仓库名称或产品文案先行给企业定性。

## 15. 第一版范围

### 必须具备

- Windows 桌面应用打包；
- 企业名称输入；
- 淘宝、京东、抖音、拼多多链接的尽力解析与明确降级；
- 本地截图 OCR 与企业候选确认；
- 企业主体确认流程；
- 无密钥的公开信息检索框架与首批连接器；
- 来源分类、客观摘录、去重及基本事件关联；
- 企业回应和后续信息的并列呈现；
- “留白聚焦”主界面、结果列表和独立详情；
- 外部浏览器逐次确认；
- 本地历史、缓存清理和隐私说明；
- GitHub 源码、文档和 Windows Release。

### 可以延后

- macOS、Linux 和移动端；
- 境外企业检索、外文来源和多语言 OCR；
- 自动更新；
- 代码签名证书；
- 云同步和用户账号；
- 社区提交或企业申诉后台；
- 高级本地语言模型摘要；
- 大规模中心化索引；
- 多语言界面。

## 16. 验收场景

1. 普通用户在全新 Windows 电脑上，无开发环境、无账号、无密钥，能够安装并打开应用。
2. 用户输入企业名，确认主体后看到带来源、日期、摘录和原文链接的结果。
3. 用户粘贴四个平台中的商品链接；能解析时展示候选主体，不能解析时明确建议截图或手动输入。
4. 用户上传包装截图，OCR 在本机提取厂商文字并允许修正。
5. 个人公开陈述明确标注“个人陈述/尚未独立核验”，不会显示为正式处罚。
6. 同一事件存在企业回应或后续时，在详情中关联展示。
7. 自动检索不足时，软件不自行打开浏览器；只有用户确认后才打开预览过的查询。
8. 无结果时，软件明确说明结果可能不完整，不暗示企业“没有问题”。
9. 用户可以删除一条历史、清空全部缓存，并确认截图未被默认长期保存。
10. 断网、来源超时或某一连接器失效时，应用不会崩溃，其他本地功能与已有结果仍可使用。

## 17. 留给开发者的可逆决定

以下事项可在实施计划中通过小型技术验证后决定，不改变产品意图：

- Electron 或其他成熟桌面 Web 容器的最终选择；
- 前端状态管理和本地数据库库；
- 本地 OCR 引擎；
- 首批无密钥公开来源连接器；
- 安装器与免安装包的具体格式；
- 缓存时长、并发数和超时等工程参数；
- 是否在首版开放深色主题。

任何会改变中立呈现、隐私默认值、免费免密钥承诺或浏览器确认机制的决定，均不属于开发者可自行变更的范围。
